--- Analysis (v1, at the time) ---
The loadStatus observer DID fire on the Task thread (proving field/observer dispatch works
cross-thread for a Task-owned node). Reading `m.p.loadStatus` inside the observer raised runtime
error &hec ("Dot operator on invalid component"). Initial read: `p` itself had become invalid.

Notably, `PROBE|014` (the line immediately after the `p.uri = ...` write, in the SAME calling
function) never printed -- the asynchronous observer callback preempted the main probe thread
before it reached its own very next statement.

--- REVISED after the v2 crash (see below) ---
v2 (same class of bug, a different line) shows `m.posterObservedCount = m.posterObservedCount + 1`
raising "Type Mismatch. Operator '+' can't be applied to 'Invalid' and 'Integer'" -- a plain missing
-AA-key read (`Invalid`), not a dead-COM-reference error. That reframes v1 too: `m.p` was most likely
just ABSENT from the observer's `m` (a normal missing-key read returns `Invalid`), and the dot
operator on that `Invalid` value is what raised &hec -- not that the live `Poster` node itself had
been destroyed.

The real finding: **the observer callback body runs with a DIFFERENT `m` than the code that called
`observeField()`/set the local variables** -- theory (user-proposed, matches the evidence): a
rendering node like `Poster` is owned by the render thread, so its field observers dispatch there
too, using a fresh/separate `m` for the Task component (seeded with only `top`/`global`, matching
`count:2`-3 in both crash dumps) rather than the Task's own live execution-thread closure. Runtime
locals set procedurally on the Task thread (`m.p = p`, `m.posterObservedCount = 0`) never appear in
that other `m`; only the actual component instance (`m.top`) and its declared interface fields
would be expected to carry over consistently.

The probe was hardened after each crash (see README) to diagnose this without needing the debugger:
`try`/`catch` around every risky access, and printing `m.count()`/`m.DoesExist(key)` at the top of
every observer body to show exactly what that `m` actually contains before touching it.

--- Analysis: this is the answer ---

Full run, zero crashes, all four phases complete. Two clearly different behaviors:

1. **`poster-direct`/`animatedimage-direct` (direct CreateObject + observeField from the Task's own
   top-level script): the `m`-divorce theory is CONFIRMED.** Every observer firing shows
   `m-count=2`, `has-p=false`/`has-a=false`, `has-posterObservedCount=false`/`has-animObservedCount=
   false` -- the observer body runs with a separate, near-empty `m` (just `top`/`global`), so it can
   never see script locals the creating code set. The underlying NODE itself is fine, though: the
   creating script's own synchronous reads (`PROBE|015`, `PROBE|025`) and the poll loop (which reads
   through the ORIGINAL `p`/`a` reference, not through the observer) show completely normal
   progression (`loading`->`ready`; `stop`->...->`decode`, settling and staying correct). This is a
   real Roku quirk for this exact usage shape -- a genuine pitfall for app authors, but not a
   simulator correctness gap: it's about which `m` a callback runs with, not about whether the node
   loads or the field ends up right.

2. **`poster-xmlattr`/`animatedimage-xmlattr` (uri as an XML attribute on a child of a Task-created
   custom component, observed from that CHILD's own init()): works completely normally.** `m-count=
   3`, `has-p=true`/`has-a=true`, `has-top=true` -- full, correct `m` context every time. Values
   progress exactly like the render thread (`init`->`first`->`decode` for AnimatedImage, matching
   the render-thread-fixed vocabulary exactly), the observer fires the expected number of times
   (`observedCount=3`), and NOTHING gets stuck.

Conclusion: engine finding #1 (Field.deliverPendingConstructionCallbacks() never draining on Task
threads) is a REAL, reachable divergence after all -- this is exactly the "xmlattr" shape, a common,
idiomatic pattern (a Task-owned wrapper component around a preloaded rendering node), and on device
it just works. The engine currently leaves it stuck forever instead. This should be fixed.
